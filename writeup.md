The fuzzer exists in the run_main.py file which has multiple Class structures set up across several files to enable easy modification of implemented file types and addition of future ones. It currently is capable of fuzzing plaintext, JSON, CSV, XML, JPEG, PDF and ELF binarie.

When the fuzzer is run it grabs all files either submitted directly too it or that are available within the binaries path. It takes every binary and checks the valid input type before initialising the specific file type fuzzer and running its generate function. This allows it to complete large scale fuzzing of specific file types or even multiple different file types with minimal user input. It can also be run on a specific binary by directly submitting the file name 
when running the fuzzer. 

The classes approach allows us to reuse the fuzz_binary function instead of creating specific functions for each, streamlining debugging and allow us to create change across the whole system rather than just one at a time. The harness is also set up to use threads, this massively speeds up the process of fuzzing and helps the harness produce the maximum amount of inputs within the 60 second time limit for each binary. 

The fuzzer then repeatedly sends the generated data to the target binaries and checks to see if the binary has crashed, if this occurs it will print the exact iteration and exit code. If the fuzzer encounters a potential hang, which it considers after the binaries goes unresponsive for more than 0.5 seconds, it will print the specific iteration number that caused the hang as well as a warning. Fuzzing will only stop under two conditions, if a crash is found or if 60 seconds have passed with no crashes. The harness will also print a status update every 100 iterations with a runtime check.

Once the fuzz_binary function has completed we save the unique crashes and hangs to a text file with the same name as the binary. This output will change depending on the type of event. Crashes contain the interation, exit/ error code, a representation of the input in hexadecimal and the first 100 characters of input represented as a string. Hangs are similar but do not produce an exit code, instead they are marked with a boolean named Timeout/Hang and the include the 0.5s buffer time that the harness waited. The outputs are written to both a text file and a json file in order to easily see and use the outputs.

From here we will discuss each fuzzer indepth. This will include some of the specifics on how the fuzzer generates inputs and what mutations of pre-exisiting inputs it attempts. These write ups do not include every single strategy these fuzzer's attempt and only give a base overview of some of the mutations they use.

The plaintext generator is the basic fallback file input for our fuzzer, it starts with some basic edgecases before producing structure aware mutations, this preserves the format of the example inputs while mutating values within it. The fuzzer with then attempt a wide array text focused mitations like format strings, boundary distortions and whitespace insertions. Finally it attempts some combined mutations before entering a permanent loop if none of these produce a crash.

The JSON generator generates a empty files, large files, invalid JSON, files containing format strings, files with deeply nested objects, extremly large numbers for integer overflow and a long string for buffer overflow. The JSON class also runs a mutation on some of the parsed data which will randomly either remove a key, add a new key, modify a value, create a deeply nested structure or attempt to duplicate a key (invalid JSON). 

The CSV generator uses a similar framework to the JSON fuzzer but focuses on mutating rows and fields in ways that can break CSV parsers. It generates different types of common inputs, such as empty or oversized inputs, and mutates data by changing individual fields (adding quotes, replacing commas, inserting newlines), as well as performing row-level mutations that can reverse, delete, clear, or duplicate entire rows. During fuzzing, the harness sends the generated inputs to the target binary, which monitors for crashes or unexpected exits. 

The XML generator class utilizes both structured payload generation and mutation based fuzzing to try create volatile input that might crash or break any XML passing binary. Firstly the fuzzer focuses on more structured mutation such as oversied tags, format strings, attribute bombs, invalid utf-8 characters and deeply nested tags. After this has been completed it then will enter a permanent loop with 10 mutation based strategies. This includes simple byte level mutations, further deep nesting mutations, extreme payload size, control character insertion and randomised format string payloads. 

The JPEG generator targets both metadata and image segment data. It initially will try edge cases such as empty input, incomplete headers, overflow and extreme dimensions. It then starts to focus on more structure aware mutations such as corrupting existing JPEG markers, adding new or deleting markers, Huffman and Quantization table mutations and start of frame and start of scan mutation. Once this is complete it also mutates the image-data by flipping bytes, inserting escape sequences and having some overflow payloads. Once this is completed it will randomly reattempt these mutations.

Like the JPEG generator, the PDF generator targets the metadata and document structure as well as the actual stream data. Once again the process starts with some basic deterministic seeds for common errors such as duplicated headers, javascript payloads, and format strings. Once these are completed it randomly mutates inputs until a crash is found or the fuzzer times out. These mutations include length corruption, byteflipping inside the stream data, mutations to the PDF trailer, xref mutations such as injecting invalid entries and object rotations. Should any of these mutations fail to produce a valid input there is also a simple byte mutation check that can be completed instead.

The ELF fuzzer starts with some common errors such as only magic bytes, incomplete and only headers as well as truncated files. Once these are complete it attempts some basic mutations such as magic byte mutations, dummy sections, extreme file sizes and  mutations in both the program and section headers. It will also attempt some table mutations and rotations and content mutations. Once each strategy has been attempted the generator will attempt 100 additional mutations which combine 2-4 previous strategies into a single input.  This allows for some more complex payloads which may cause a crash. 

It is also effective at finding bugs such as buffer overflows, parsing errors, or crashes caused by inconsistent row lengths and invalid delimiters. Future improvements could include adding grammar-aware mutation (respecting proper CSV escaping), feedback-based mutation guidance, and better crash deduplication.
